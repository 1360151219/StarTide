# 《星潮守望者》角色中心视觉审计

> 视觉方向：D「日光远征动画」
> 审计日期：2026-08-11
> 审计对象：角色中心「状态 / 装备 / 技能」三个分区
> 实机画布：540×960、540×1170、540×1200、720×960
> 本轮性质：方案 A 细化复验；未修改游戏逻辑、数值、内容 ID、存档或音频 Cue

## 1. 结论

角色中心装备分区已按方案 A 完成落地：页面标题使用独立帆布签，英雄切换改为同源头像页签，栏目和背包筛选改为纯图标索引；英雄台加入帆布内衬与左三右三六槽，等级与战力进入独立的晨湖青 / 暖象牙远征战力牌，背包改为五列 `88×88` 正方形网格。普通 / 稀有 / 顶级分别使用灰色单压线、鲜绿双压线、明亮金色三段边框，已装备物品在右上叠加同源英雄头像。

装备分区已经达到与首页接近的成片度，首读顺序稳定为「当前英雄 → 六槽装备 → 战力 → 五格背包」。战力数字提升至 36 px 日照金固定值列，背包托盘扩大至 252 px 并下探到 Bottom Bar 上方 8 px；数量与状态文案均退出底框和右下织带干扰区。当前页面剩余的主要矛盾已转移到状态与技能分区：这两页仍有卡中套卡和同构列表，角色身份连续性弱于装备页。装备页自身还缺少物品飞向槽位、稀有 / 顶级揭示等因果动画。

本轮判断：

- 角色辨识、装备基础辨识、色彩和字体系统：通过。
- 装备页的视觉层级、信息可读性、材质、品质与间距：通过；动画反馈部分通过。
- 技能辨识：当前默认档案全部为未发现态，只能审计锁定结构，不能据此判定已发现技能的最终辨识质量。
- 网页模板感：装备页 `1.5/5`，角色中心整体 `2.5/5`；残留主要来自状态页嵌套卡和技能页同构行。
- AI / 拼贴感：装备页 `1/5`，角色中心整体 `1.5/5`；新增素材已统一为帆布、桦木、搪瓷与暖金语言。

## 2. 审计方法与边界

- 实际启动主场景，分别进入状态、装备、技能三个分区；装备分区在 540×960、540×1170、540×1200、720×960 四档画布检查，并额外构造普通 / 稀有 / 顶级与跨英雄归属状态。
- 同时检查装备页稳定帧与战力变化中的过渡帧，避免把瞬时动画误判为静态排版。
- 以 `ART_DIRECTION.md`、`UI_SPEC.md`、`ASSET_MANIFEST.md` 和定稿首页参考为唯一判断基准。
- 以 200 ms 首读、灰度轮廓、最小字号 14 px、触控区 48×48 px、文字距结构线 12 px 为检查阈值。
- 本轮隔离档案中三项技能均为未发现态；报告不会为审计方便伪造解锁状态，也不会修改任何玩法数据。
- 设计稿只用于方向审阅，所有文字与数字位置保持为空；它们不是运行时整图，不登记为正式素材。

## 5. 分区结论

### 5.1 状态

- 优点：摘要、经验、四项核心属性和一次战绩信息已经足够精简；数字固定列清楚。
- 主要问题：英雄只是卡内缩略图，外层卡、摘要卡、属性卡三层矩形叠加；页面有信息但没有「人物档案」的游戏场所感。
- 推荐方向：连续远征档案卷。角色、进度和属性共享一张卷面；四项属性只保留图标、字段和固定值列。

### 5.2 装备

- 已完成：标题签、双英雄头像页签、三枚栏目图标、帆布内衬、左三右三六槽、独立等级 / 战力牌、三档品质正方形格、五列浅托盘、四枚筛选图标和右上归属头像均已接入运行时。
- 优点：英雄是全页第一焦点；六槽、鲜明战力牌和背包形成清楚的二三级层级；普通灰、稀有绿和顶级金在关闭文字后仍可依靠压线层数区分。扩大后的托盘完整包住五格、数量和状态提示，并把与 Bottom Bar 的结构空隙收至 8 px。
- 主要问题：详情抽屉与装备落位动画尚未达到静态页的完成度；多于五件时的滚动提示仍可精修。

### 5.3 技能

- 优点：文案已经从三段重复说明收敛为一次全局提示，技能点和重置关系明确。
- 主要问题：三条同构锁定行是全页网页模板感最强的区域；当前未发现态无法验证技能辨识。
- 推荐方向：用一条连续织带训练路径承载三个节点。锁定态遵守「锁徽章 + 未发现」；已发现态依靠星枪、环轨、潮汐等轮廓区分，不能只换颜色。

## 6. 三张设计稿的方向定义

三张稿都属于同一个方向 D，不是三套互相竞争的美术风格；它们分别验证角色中心最需要解决的三种结构。

| 方案 | 重点 | 解决的问题 | 成本 / 风险 | 建议 |
|---|---|---|---|---|
| A「英雄台优先」 | 大英雄舞台 + 左三右三六槽 + 五列浅背包托盘 | 焦点、装备辨识、背包空白、材质断层 | 已落地并通过四档画布复验 | **当前全页结构母版** |
| B「远征档案」 | 角色与四项属性共用一张不对称档案卷 | 状态页卡中套卡、英雄过小、数字表格感 | 中等；需控制卷面面积，避免重新变成大白卡 | 作为状态分区的内容结构 |
| C「技艺路径」 | 三个技能节点沿连续织带排列 | 技能列表感、技能轮廓弱、培养来源不清 | 较高；需同时定义发现 / 锁定 / 可培养 / 满级状态 | 作为技能分区的内容结构 |

落地时不应把 A、B、C 做成三套互不相干的页面。正确做法是：以 A 的顶部身份梁、背景、底部导航和材质为共享骨架；状态区替换为 B 的档案卷；技能区替换为 C 的训练路径。这样只需要一套导航、一套材质和两种面板母形。

## 8. 下一轮验收条件

1. 200 ms 首读顺序稳定为「当前英雄 / 当前分区内容 / 关键数值 / 次级操作」。
2. 状态与技能分区的场景文字也全部进入实色承载底，不再直接压在树叶、帐篷、绳索和高频纹理上。
3. 页面只保留两种主面板母形；关闭纹理后仍能用轮廓区分英雄台、槽位、背包和技能节点。
4. 装备变化能从物品卡追踪到目标槽位，再反馈到战力；技能培养能从动作按钮追踪到技能节点。
5. 已发现的三项技能在 20 px 灰度下可互相区分；未发现态不泄露技能内容。
6. 详情抽屉中的长装备名和本地化文案不会静默裁切；背包格不重新塞回名称或属性，底部信息行不得侵入底框与右下织带，最小功能字号保持 14 px。

8. 设计稿中的空白字段全部由 Godot 节点承载文字和数字，生成图不得进入运行时整页背景。
